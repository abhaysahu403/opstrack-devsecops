# OpsTrack DevSecOps Demo Guide

A ~10–15 minute walkthrough script for demonstrating the full pipeline:
code → PR → test → quality → security → Docker → artifacts → HTML reports →
GitHub Actions Summary → GitHub Pages → ZIP download → merge.

Terraform/GCP deployment is **not** part of this demo — the story ends at
"image built, scanned, and pushed to GHCR." See README §14 if you've added
your own deployment step on top of this.

## Before you start

* Push this repository to GitHub and confirm `main` is protected (README §17).
* Set **Settings → Pages → Source: GitHub Actions** so the dashboard has
  somewhere to publish to.
* Optional but recommended for a richer demo: add `SONAR_TOKEN` +
  `SONAR_HOST_URL` and/or `SNYK_TOKEN` as repository secrets beforehand so
  those stages show `PASS` instead of `NOT CONFIGURED`.
* Run `docker compose up --build` once locally and confirm
  `curl http://localhost:8080/health` returns `{"status":"UP"}`, just so
  you know the app itself is healthy before you start narrating.

## Step 1 — Show the repository

Walk through the top-level layout: `cmd/`, `internal/`, `migrations/`,
`.github/workflows/`, `reports/`. Point out this is a real, moderately
sized Go service (services + incidents), not a toy.

## Step 2 — Show the protected `main` branch

Settings → Branches. Point out the required PR + status checks rule
(README §17).

## Step 3 — Create a feature branch

```bash
git checkout -b feature/add-incident-filter
```

## Step 4 — Make a small code change

Something small and visible — e.g. add a comment, tweak a validation
message in `internal/validation/validation.go`, or add a new filter
parameter. Keep it trivial; the point is to trigger the pipeline, not to
write a feature live.

## Step 5 — Open a PR

```bash
git add -A
git commit -m "demo: small change to trigger the pipeline"
git push -u origin feature/add-incident-filter
```

Open the PR against `main` on GitHub.

## Step 6 — Show GitHub Actions starting automatically

Switch to the **Checks** tab on the PR (or the **Actions** tab). Point out
three jobs kick off in parallel: `Test`, `Security & Quality`,
`Docker Build & Scan` — all defined as reusable workflows
(`.github/workflows/reusable/*.yml`) called from `pr-validation.yml`.

## Step 7 — Show tests

Click into the `Test` job. Walk through: gofmt check → go vet → build →
`gotestsum` unit tests with a JUnit report → coverage → integration tests
against a real Postgres **service container** → `golangci-lint`.

## Step 8 — Show SonarQube

Click into the `Security & Quality` job's `sonarqube` sub-job. If
configured, show the link to the SonarQube project dashboard rendered in
`reports/sonar/index.html`. If not configured, this is a good moment to
explain the `NOT CONFIGURED` status — the pipeline never fakes a passing
scan for a tool that didn't actually run (README §10).

## Step 9 — Show Trivy / Snyk / Gosec

Same job, different sub-jobs: `gosec`, `trivy-fs`, `snyk`. Each writes a
JSON (machine-readable) and an HTML (human-readable) report.

## Step 10 — Show generated artifacts

Back on the workflow run summary page, scroll to **Artifacts**. Point out
the per-stage artifacts (`reports-test`, `reports-gosec`, …) and the
combined `opstrack-ci-reports-pr-<number>` artifact.

## Step 11 — Open the GitHub Actions Summary

On the same run page, open the **Summary**. This is generated by
`scripts/write-step-summary.sh` from `$GITHUB_STEP_SUMMARY` — show the
Build/Tests/Security/Code Quality/Docker/Reports sections.

## Step 12 — Open the GitHub Pages dashboard

Note: Pages is only updated on `main`, not on PRs (README §13) — if this is
the first run, you'll show the dashboard *after* merging in Step 15. If
`main` has already run once, open:

```text
https://<org-or-user>.github.io/<repo-name>/
```

Point out the color-coded per-stage badges and that "Build Status" reflects
the actual aggregate of all jobs.

## Step 13 — Open individual HTML reports

From the dashboard, click into two or three: Unit Tests, Coverage, Trivy
Filesystem. These are the same `reports/<tool>/index.html` files bundled in
the ZIP.

## Step 14 — Download the ZIP

Click **Download All Reports (ZIP)** on the dashboard (or the
`opstrack-ci-reports.zip` file inside any of the artifact downloads).
Briefly open it locally to show it's a real, self-contained bundle.

## Step 15 — Merge the PR

Merge the PR into `main`. This triggers `main.yml`.

## Step 16 — Show the Docker image / artifact

Open the `main.yml` run → `Docker Build, Scan & Publish` job. Show the
image being built, scanned with Trivy, then tagged and pushed to
`ghcr.io/<org>/<repo>:latest` and `:<git-sha>` (visible under the repo's
**Packages** tab).

## Step 17 — (Optional) Talk through what deployment would look like

Since GCP/Terraform isn't part of this build, this is a good place to
narrate rather than demo: "the image that just got pushed to GHCR is a
single, stateless container that reads `DB_*` / `SERVER_PORT` from the
environment — pointing it at a VM, Cloud Run, or anywhere else is a small
follow-on `deploy.yml`, deliberately left out of this prototype." (README
§14 has the specifics if someone asks.)

## Step 18 — Call the live `/health` endpoint

If you have the app running locally (`docker compose up --build`) or on
any host, close the loop:

```bash
scripts/health-check.sh http://localhost:8080
# or, against wherever you're running it:
scripts/health-check.sh https://your-host.example.com
```

---

### Talking points if something is red

* **A stage shows `NOT CONFIGURED`** — expected for Snyk/SonarQube without
  their secrets; not a failure. See README §10/§16.
* **Trivy shows findings but the job is green** — severity gating defaults
  to report-only (README §10); flip `trivy-fail-on-critical-high` to `true`
  to make CRITICAL/HIGH findings fail the build.
* **Want to show a failing PR safely** — push an intentionally failing test
  or an obviously insecure snippet (e.g. `md5.Sum` used for a password) on
  a throwaway `demo/broken-check` branch, open a PR from it, show the red
  `X`, then close the PR without merging. Never leave the change on `main`.
